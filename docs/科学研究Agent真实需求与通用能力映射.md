# 科学研究 Agent：真实需求、工程模块与闭环建设建议

> 版本：2026-07-25
> 输入：`/Users/zhangyanggao/Downloads/科学研究Agent 需求采集模板.md`
> 目的：给产品与工程团队一份可直接用于能力拆分、排期、验收和真实科研试点选择的统一需求文档。

## 0. 执行摘要

模板中的论文阅读、知识整理、数据清洗、Baseline 生成、结论可信度审查、Idea 验证、投稿自审和 Benchmark 适配都是真需求，但整体仍偏向“单用户、单次会话、纯数字世界”。多领域并行分析后，最值得建设、也最难由普通 Codex 直接闭环的需求集中在以下问题：

1. **一个结论到底从哪里来**：不仅需要参考文献 URL，还要追到确定版本中的页、段、图、表、公式、数据行、代码、运行环境、样本和人工决定；上游变化后还要找出全部受影响下游。
2. **任务结束不了或不能重来时怎么办**：数小时至数月的训练、仪器运行、冷链运输、野外采集和受试者随访必须可持续、可恢复、可交接，不能靠一个聊天会话“在线陪跑”。
3. **多个线程同时 Computer Use 时如何不串键鼠**：每线程必须拥有独立虚拟显示器、鼠标、键盘事件队列和窗口焦点；共享云文档、GPU 或仪器则由另一层业务资源租约处理。
4. **科研协作不是共享一个文档**：共同共编、独立盲审、顺序交班、跨站点联邦是四种不同甚至相反的协作语义。
5. **科研工作发生在不同终端和物理世界**：手机负责扫码、拍照、录音、定位、离线采集和告警；桌面负责私有数据、计算和仪器软件；网页负责共同审阅、任务和组织管理。
6. **“不知道、未发现、不应继续”也是成功结果**：系统必须保存负结果、失败实验、停止决定、搜索覆盖边界和未解决分歧，而不是总要生成一个肯定答案。

建议把平台定位为：

> **成熟 Agent runtime 负责通用推理与执行，SciForge 负责科研对象、证据、长期状态、资源隔离、人类责任和跨端控制。**

建议工程实施收敛为六个模块：

- **F1 证据与产物版本服务**；
- **F2 线程隔离的 Computer Use Runtime**；
- **F3 持久任务编排器**；
- **F4 多人科研工作区**；
- **F5 多客户端同步与通知**；
- **F6 连接器与外部写入网关**。

版本不可变、身份、最小权限、审批绑定、幂等、动作回执和审计是每个模块自然必须满足的基础不变量，不再包装成额外“功能”。

首个软件侧闭环建议选择“**实验数据清洗多人会审**”；第二个计算闭环选择“**无源码论文 Baseline + HPC 长任务 + 独立复现**”；之后再做“**仪器异常跨班次处置**”和“**野外离线样本链**”。这样先验证通用底座，再进入物理高风险场景。

## 1. 分析口径

### 1.1 “Codex 无法直接满足”不等于“Codex 永远不能参与”

官方资料显示，Codex/模型可以通过 Browser 或 Computer Use 打开页面、点击、输入、查看截图并验证页面状态；API 侧也支持用自定义 harness 驱动浏览器或桌面。官方同时明确建议在隔离浏览器或 VM 中运行，并在高影响动作前保留人工确认。[Codex Browser 文档](https://learn.chatgpt.com/docs/browser#computer-use-in-the-browser)、[OpenAI Computer Use 指南](https://developers.openai.com/api/docs/guides/tools-computer-use)

因此本文中的“无法直接满足”指普通 Codex 任务默认不提供以下**系统级保证**：

- 机构身份、角色、法定签名和职责分离；
- 跨会话、跨重启、跨月的权威科研状态；
- 多人实时协作、盲态隔离、交班和跨站点策略；
- 样本、试剂、仪器、传感器等物理对象的真实状态；
- 多线程 GUI、账号、凭据和共享资源的强隔离；
- 从原始数据到图表和论文结论的强制证据链；
- 对外写入的幂等、补偿、审批、审计和完成证明；
- 设备安全认证、硬件联锁或临床/伦理责任。

Codex 仍然可以是这些闭环中的规划者、执行者、代码生成者或分析者；需要新增的是其外部的科研控制面与证据层。

### 1.2 现有 SciForge 资产：增强，不重建

只读代码和文档审查显示，仓库已经具备重要基础：

- Evidence DAG 已有不可变 Evidence Snapshot、Artifact/ArtifactVersion/SourceAnchor、结构化运行血缘、L0–L4 provenance、PROV/RO-Crate/DataCite 导出。
- Project DAG 已能聚合跨会话证据、冲突、Decision、Review 和发布状态，并执行访问策略。
- Computer Use 已有 GUI-Owl sidecar、MCP 包装、执行授权、安全诊断和 active lease 状态展示的基础结构。
- 已有远程执行、Schedule、Connect phone、Workspace Preview 和科学对象插件基础。

参考：

- [Evidence DAG worker](../packages/workers/evidence-dag/README.md)
- [Project DAG worker](../packages/workers/project-dag/README.md)
- [GUI-Owl Computer Use](../packages/workers/gui-owl-computer-use/README.md)
- [SciForge 产品定位](../README.md)

本建议的重点不是增加第二套 Evidence/Computer Use/协作旁路，而是沿现有公共合同补齐：

- 跨系统自动采集、动态来源状态和下游失效传播；
- 线程身份、目标资源、租约、fencing token 和幂等回执端到端传递；
- 多人身份与四种协作拓扑；
- 桌面/网页/手机共用同一对象、事件、权限和任务状态；
- 仪器、样本、现场传感器和临床系统的 package-owned 连接器。

### 1.3 不按学科或“Agent 名称”分类

“论文 Agent”“数据 Agent”“实验 Agent”会把同一套版本、审批、证据、执行和权限逻辑重复实现。建议把**一项需要负责的科研工作或决策**作为分类单元，用多维标签描述。

## 2. 科研需求的正交分类法

建议使用：

`Need = 生命周期 L × 闭环介质 C × 风险 R × 时效 T × 协作范围 S × 协作拓扑 K × 证据强度 E × 数据敏感度 D × 人类决策 H`

### 2.1 分类维度

| 维度 | 建议枚举 | 工程含义 |
| --- | --- | --- |
| 生命周期 L | L0 立题；L1 检索；L2 Idea 查新；L3 方案/协议；L4 采集/质控；L5 分析/建模/复现；L6 结论审查；L7 写作/投稿；L8 传播/管理；L9 长期维护 | 决定 workflow、validator、rubric 和默认验收，不应进入 Host 的领域硬编码 |
| 闭环介质 C | C0 信息；C1 代码/计算；C2 数字工作区/外部系统；C3 组织协作；C4 物理仪器/样本 | 决定连接器、沙箱、事务、回滚和物理安全边界 |
| 风险 R | R0 只读建议；R1 可逆草稿；R2 受控写入/算力；R3 改变数据、口径或正式结论；R4 人体、动物、仪器或高危物理动作 | R3/R4 必须结构化人工批准；不得由模型自信度放行 |
| 时效 T | T0 秒级；T1 单会话；T2 小时/天；T3 周/月；T4 事件触发/紧急 | 决定队列、检查点、后台持续性、通知和 SLA |
| 协作范围 S | S0 个人；S1 课题组；S2 跨团队/机构；S3 外部评审/公开 | 决定身份、权限、数据驻留和外发策略 |
| 协作拓扑 K | K0 单人；K1 共同收敛；K2 独立隔离；K3 顺序接力；K4 跨站点联邦 | 决定共编、盲态、唯一控制权或数据不出域状态机 |
| 证据强度 E | E0 表达辅助；E1 来源可定位；E2 claim→原文/图表/数据；E3 输入→运行→输出可复现；E4 独立重复/反证/监管审计 | 多数正式科研产物至少需要 E2，计算结果通常需要 E3 |
| 敏感度 D | D0 公开；D1 未公开；D2 合作/个人受限；D3 医疗、专利、双用途、出口管制 | 决定本地/私有部署、出站 DLP、脱敏和保留策略 |
| 人类决策 H | H0 无；H1 范围确认；H2 歧义/异常；H3 写入前批准；H4 科学、伦理、法律责任 | 决定谁在什么版本上确认什么，不能只问一句“是否继续” |

### 2.2 四种科研协作拓扑

| 拓扑 | 真实场景 | 核心语义 | 必需平台原语 |
| --- | --- | --- | --- |
| K1 共同收敛 | 共写论文、共同标注、组会报告 | 多人围绕同一 artifact 收敛 | 共编/提案合并、评论、冲突处理、作者归属 |
| K2 独立隔离 | 盲审、双人抽取、独立复现 | 提交前互不可见，提交后比较与仲裁 | sealed branch、信息屏障、揭盲条件、差异对齐、第三方裁决 |
| K3 顺序接力 | 值班、仪器控制、长训练接班 | 任一时刻恰有一个责任人/控制者 | owner lease、offer/accept 交班、心跳、超时升级、exactly-once |
| K4 跨站点联邦 | 多中心医疗、企业—高校合作 | 数据留在各域，只输出策略允许的结果 | compute-to-data、策略握手、签名结果、跨域 lineage、撤回规则 |

同一闭环可以组合拓扑。例如，多中心双盲数据抽取是 `S2 + K2 + K4`；夜间仪器运行后共同写报告是 `S1 + K3 + K1`。

## 3. 真实科研需求目录

下表同时包含模板中的需求和 sub-agent 补充的高价值场景。能力编号见第 4 节。

### 3.1 检索、证据、论证与科研表达

| ID | 真实触发与痛点 | Agent 应完成的闭环 | 必须由人完成 | 可验收结果 | 普通 Codex 的直接缺口 | 能力 |
| --- | --- | --- | --- | --- | --- | --- |
| N01 论文阅读辅助绘图 | 一个 topic 涉及多篇论文、公式和复杂逻辑；普通总结冗余，图中箭头易混入模型推断 | 论文集合→claim/公式/图表证据→多张可编辑图→截图讨论→发布快照 | 决定叙事重点和最终科学表达 | 每个数字、公式、箭头能回到具体版本与位置；事实、综合和推断分型 | 生成图片容易，无法默认保留图中元素到原证据的强链接 | P1、P2、P6、P8 |
| N02 活的知识报告 | 文献、新闻、书籍持续变化；一次报告很快过期 | 检索协议→去重/聚类→冲突证据→报告→增量更新→影响提醒 | 确认范围和重要性 | 每个 claim 有来源；记录数据库、query、时间和排除理由；更新不覆盖旧版本 | 缺少长期来源监测和下游影响图 | P1、P3、P6、P12 |
| N03 Idea 新颖性边界 | 搜不到不等于没人做过，传统关键词搜索又难覆盖模糊想法 | 意图结构化→多数据库检索→相似工作对齐→“在已检索范围内未发现”→持续监测 | 判断研究价值和投入 | 负向结论必须有数据库、query、日期、语言和筛选快照 | 单次搜索无法证明覆盖边界，也不会持续更新 | P1、P2、P3、P12 |
| N04 科学结论可信度 | 论文结论可能超出数据，不同证据强度不可用影响因子粗暴替代 | 原子 claim→支持/反驳/限定证据→偏倚/复现/独立性评价→分歧裁决 | 决定 rubric、权重和争议解释 | 质量与支持方向分开；相关性不标成因果；保留反对意见 | 模型自信度不是科学可信度，缺少强制 evidence graph 与独立复核 | P1、P2、P6、P8、P9 |
| N05 更正/撤稿影响分析 | 引用后很少有人持续检查更正、撤稿、预印本—正式版变化 | 保存来源快照→监测状态→找出受影响 claim、图、报告和决策→重审 | 决定重算、改写或保留警告 | 旧版本不删除；状态事件可追溯；关键下游自动转“需复核” | 一次性检查容易，缺少长期监测和反向依赖传播 | P1、P3、P6 |
| N06 失败实验与负结果记忆 | 失败、阴性结果和停止决定散落在个人记录，后来者重复踩坑 | 固化实际执行与原始证据→分类失败→检索相似历史→签署重试/停止→约束后续排期 | 解释失败类型并批准是否重开 | 严格区分计划、实际、观察和解释；强制重开需写理由 | 可以总结一次失败，不能让组织长期执行停止约束 | P1、P3、P5、P6、P8 |

| F2 | **线程隔离的 Computer Use Runtime** | 每线程独立虚拟显示器、鼠标、键盘队列、焦点、剪贴板、profile、文件挂载与画面流 |
| F3 | **持久任务编排器** | Durable job、状态机、checkpoint、恢复/取消、worker lease、HPC adapter 与 reconcile |
| F4 | **多人科研工作区** | 版本化 proposal/review/decision、共编、sealed review、handoff 与对象级权限 |
| F5 | **多客户端同步与通知** | 桌面/Web/手机共享事件流、离线队列、冲突仲裁、深链通知与设备撤权 |
| F6 | **连接器与外部写入网关** | Connector SDK、凭据代理、preview→approval→commit→verify、资源 lease 与动作回执 |

三层边界：

- **基础不变量（不是独立功能）**：版本不可变、身份与最小权限、审批绑定确定版本、幂等、动作回执和只追加审计。
- **工程模块（F1–F6）**：有独立服务边界、API、首批任务和自动化验收，由工程团队直接负责。
- **领域适配包**：PDF/公式/科学数据 schema、HPC、ELN/LIMS、样本、仪器、时空和临床 validator/connector，由 domain package 贡献。

旧 P1–P12 编号在第 3 节需求表中暂作为**分析标签**保留，工程排期和验收一律使用 F1–F6。映射原则如下：

| 分析标签 | 工程归属 |
| --- | --- |
| P1/P2/P9 | F1 为主；长时间运行部分进入 F3 |
| P4 | F2；共享业务资源 lease 不属于键鼠隔离，进入 F6 |
| P3/P11/P12 | F3 为主；通知升级进入 F5 |
| P6/P8 | F4；外部写入的审批与策略检查进入 F6 |
| P7 | F5 |
| P5/P10 | F6 + 领域适配包 |

### 4.2 核心对象模型

平台只保留一套通用 Research Work Graph：

```text
Project
 ├─ Task / Workflow / Protocol
 ├─ Artifact ─ ArtifactVersion ─ EvidenceFragment / SourceAnchor
 ├─ Claim ─ Assessment / ConflictSet
 ├─ Transform / Run ─ Environment ─ Output
 ├─ Decision / Approval / Signature
 ├─ Actor / Role / Policy
 ├─ PhysicalObject / Resource ─ Lease
 └─ Event / StatusEvent / Notification
```

关键不变量：

- 原始 Artifact 只能 append/version，不能覆盖。
- 来源原文、Agent 推断和人类裁决是不同类型对象。
- 任何正式写入只走一条 `preview → approval → commit → verify` 路径。
- 任何审批都绑定 artifact version、evidence snapshot、action plan、target resource 和 limits。
- 任一绑定内容变化，旧审批自动失效。
- 任一上游对象变化，沿依赖图把下游标记为 `Stale / Revalidation Required`，不静默重算或改文。
- Domain package 通过 manifest 贡献 importer、schema、validator、rubric、workflow、tool adapter 和可选 UI；Host 不维护领域 ID switch 或 MIME 特例。

### 4.3 P1：证据追溯插件增强

#### 目标

任意科研论断能反向追到确定版本的来源、原始数据、代码、环境、实验记录、图表和人工批准；任意上游变化能正向列出受影响结论、报告、图表和任务。

#### 必须支持的证据锚点

| 介质 | 稳定锚点 |
| --- | --- |
| PDF | 文件 hash、版本、页、字符区间、摘录指纹、页面 bbox、章节、图/表/公式编号 |
| HTML | 快照 hash、canonical URL、DOM path、Text Quote Selector、访问时间 |
| Markdown/LaTeX/XML | commit、路径、稳定 block/AST ID、字符区间 |
| 数据集 | 数据版本、表、主键/行 ID、列、切片条件、单元格 |
| 代码/Notebook | repo、commit、文件、symbol、行、cell ID、执行序号 |
| 图像 | 版本、像素 bbox、OCR、panel/legend 标识 |
| API/数据库 | 请求参数、响应快照、数据库版本、时间、结果 hash |
| 仪器/样本 | 设备 ID、校准、run ID、样本/孔位、观测时间、原始文件 |

#### 增强点

- 搜索过程本身成为证据：数据库、query、日期、过滤/排除和结果快照。
- 冲突证据并列保留，不自动平均成模糊总结。
- DOI/PMID/数据集/release 的更正、撤稿、替换和许可变化形成 StatusEvent。
- 图表逐元素可追到数据行和生成 run。
- 人类批准绑定内容 hash；内容变化后失效。
- 受限证据的摘要、缓存、索引、缩略图和导出继承最严格策略。
- 导出人读报告和机器可验证包；可与 W3C PROV 和 RO-Crate 对接。W3C PROV 用 Entity、Activity、Agent 描述来源关系；RO-Crate 可聚合研究数据、软件、设备和 workflow provenance。[W3C PROV Primer](https://www.w3.org/TR/prov-primer/)、[RO-Crate 规范](https://www.researchobject.org/ro-crate/specification.html)

#### 验收

- 标为关键的 claim 100% 有证据关系或显式 `待证实`。
- 固定测试集的 PDF/HTML/数据/代码精确定位成功率 ≥99%。
- 来源片段与目标版本 hash 一致率 100%，不存在的摘录不得通过。
- 任一关键图表可追到全部输入、代码、参数、环境和审批；断链为 0。
- 上游规则变化后，关键受影响对象召回率 100%，一般对象 ≥95%。
- 审批后内容变化 100% 使审批失效。
- 跨项目、缓存、摘要、导出和向量索引越权泄漏为 0。
- 审计包篡改检出率 100%，可离线检查引用、血缘和签名。

### 4.4 F2：线程隔离的 Computer Use Runtime

#### 准确定义

这里的“线程隔离”只回答一个问题：**不同线程的虚拟鼠标、键盘事件和显示画面是否在机制上互不干扰。**

每个线程必须一一绑定独立的 `VirtualDesktopSession`：

```text
Thread A → session-a → display-a + mouse-a + keyboard-a + focus-a
Thread B → session-b → display-b + mouse-b + keyboard-b + focus-b

InputEvent { session_id, seq, device, event }
Frame      { session_id, seq, image }
```

`InputRouter` 只能把事件注入 `session_id` 对应的 compositor / virtual HID；`FrameStreamer` 也只能返回该 session 的 framebuffer。虚拟光标 overlay、同一宿主桌面多开窗口、多个 tab 共用全局输入都不是隔离。

若两个线程最终都通过 macOS `CGEvent`、`pyautogui` 或类似机制向同一个宿主全局桌面注入事件，就**不可能并行隔离**，该 backend 必须把 `active_writer` 硬限制为 1。需要并发时：

- 浏览器任务：每线程独立 BrowserContext/profile/page/input channel；
- Linux 桌面任务：每线程独立虚拟桌面、display server/compositor 和文件边界；
- macOS 原生 GUI：每线程独立 macOS VM 或可证明独立的图形登录会话。

共享云文档、账号、GPU 或真实仪器的 writer lease 是另一类“业务资源并发控制”，进入 F6 外部写入网关，不与键鼠/显示隔离混成一个功能。

#### 第一版组件

- `SessionManager`：创建、绑定、暂停、接管和销毁线程会话；
- `SandboxProvisioner`：分配容器虚拟桌面或 VM；
- `DisplayServer/Compositor`：每 session 独立 framebuffer 与窗口焦点；
- `InputRouter`：校验 `session_id`、单调 `seq`、设备类型和会话状态；
- `FrameStreamer`：会话级截图与连续画面流；
- `ArtifactBroker`：会话级剪贴板、下载目录、profile 与文件挂载；
- `TakeoverGateway`：人类观察与接管，但不把输入广播到其他会话。

#### 第一版接口

```text
POST   /cu/sessions                 {thread_id, image, screen}
POST   /cu/sessions/:id/input       {seq, device, event}
GET    /cu/sessions/:id/frame       ?after_seq=
WS     /cu/sessions/:id/stream
POST   /cu/sessions/:id/takeover
DELETE /cu/sessions/:id
```

#### 首批工程任务

1. 所有 Computer Use 请求、输入、帧和回执强制携带 `session_id`。
2. 检测宿主全局输入 backend；并发数大于 1 时直接拒绝启动。
3. 先交付两个独立 Linux 虚拟桌面，再扩展到四会话并发。
4. 隔离窗口焦点、剪贴板、浏览器 profile、下载目录、文件挂载和截图。
5. 编写随机键鼠并发注入 harness、input flood、kill-session 和资源泄漏测试。

#### 硬验收

- 4 个会话同时输入各自随机 token、移动窗口并点击随机控件，目标会话之外零变化。
- A 移动窗口、切换焦点或输入洪泛，不改变 B–D 的 frame、focus 和事件顺序。
- 随机杀死 A 不影响 B–D 连续运行。
- A 的剪贴板、截图、cookie、下载和挂载目录对 B–D 不可见。
- 任何宿主全局输入 backend 在并发数 >1 时拒绝启动，而不是用多个虚拟光标伪装隔离。

### 4.5 P6：多人科研协作

不能只实现一个富文本在线编辑器。协作对象包括：

`hypothesis / claim / evidence / protocol / raw data / transform / code / run / figure / manuscript / comment / decision / signature / contribution`

每个对象至少需要：

`object_id, version_id, content_hash, ACL, state, parent_version, dependencies, evidence_links, created_by, change_reason`

#### 公共能力

- 统一真人、Agent、设备身份，记录委托人和实际执行 Agent。
- RBAC + ABAC：`主体 × 资源 × 动作 × 状态 × 设备/网络/时间上下文`。
- 动作细分 `read/comment/edit/run/export/delete/approve/sign/unblind/delegate`。
- comment、acknowledge、scientific approval、formal e-signature 分开。
- Draft 可编辑；Under review 只建议；Approved/Frozen 只能 amendment；Released 只能 supersede。
- 关键字段如单位、样本排除、protocol 参数和字段映射走 typed schema + semantic conflict；禁止 last-write-wins。
- 原始数据、证据、签名和审批 append-only。
- Notebook source 可以合并，kernel/execution state 必须独立或序列化。

#### 四种拓扑验收

- K1：3 人并发共编，断网重连不丢改动；冲突显式；作者/Agent/版本可归因。
- K2：揭盲前通过 API、搜索、通知、缓存、文件名、计数、审计 UI 和模型上下文均无法获知他人内容；揭盲后自动对齐差异，原始独立意见不被仲裁覆盖。
- K3：任一时刻最多一个 owner/controller；giver offer、receiver accept 后才切换；交班包含运行状态、最近动作、未决告警、预算和风险。
- K4：行级数据不离域；远端代码、模型和策略版本可证明；站点输出签名且有本地 lineage；单站失败或撤回不生成伪完整结论。

### 4.6 P7：多客户端

多客户端不是“同一网页响应式适配”，而是能力分工：

| 客户端 | 擅长 | 默认不应承担 |
| --- | --- | --- |
| 手机/平板 | 推送、扫码、照片/录音、GNSS、离线表单、ack、低风险分类和交接 | 展示全部敏感原始数据；仅凭摘要批准不可逆动作；长时间 GUI 控制 |
| 桌面 | 本地私有文件、GPU/长计算、仪器软件、完整 diff、高风险审查、隔离执行 | 作为唯一通知或协作入口 |
| 网页 | 共编、评论、看板、审阅、组织/权限管理 | 默认直接获得机构内网数据或本地硬件凭据 |

跨端恢复的是结构化 `task / object version / evidence / decision / checkpoint`，不是无差别复制所有聊天和敏感上下文。

#### 同步规则

- 离线操作带 base version、actor、device、logical timestamp、idempotency key。
- 普通文本可自动合并；样本身份、单位、排除规则、签名和审批冲突必须人工仲裁。
- 高风险审批默认在线确认最新版本；离线签名须由设备密钥签署，重连后再检查版本和权限。
- 设备本地缓存加密、可撤销；用户离组后的离线写入进入 quarantine。
- 通知记录 `generated → delivered → read → acknowledged → assigned → resolved`。
- 锁屏推送只含脱敏摘要；deep link 直达具体 project/task/object version/decision。
- 同一审批或提交从多个客户端重复触发时只生效一次。

#### 验收

- 在线并发状态 p95 2 秒内可见；断网 8 小时后重连无静默丢失或重复事件。
- 桌面发起→手机告警/审批→网页共审的状态完全收敛。
- 从通知切换客户端后 30 秒内恢复正确 task、version 和 checkpoint。
- 用户撤权后在线 session 在目标 SLA 内失效，离线写入被隔离。
- 敏感数据不出现在锁屏通知、无权端缓存或跨项目搜索中。

### 4.7 其他支撑能力

#### P3 长任务

- durable job、外部 job ID、日志 cursor、checkpoint digest、重试预算和最终状态；
- 客户端离线不影响后台任务；
- 重启后区分“排队、运行、未知、成功、失败、取消”，未知不能被推成成功；
- 失败只重跑受影响节点，保留已验证产物；
- 定时/事件监测不是无限轮询，而是有 SLA、预算和升级策略。

#### P8 策略与审批

- R3/R4 必须由具备对应角色的人确认；
- 外发、删除、破盲、仪器启动/恢复、医学/伦理决定不能由 Agent 代签；
- 沉默不是同意；超时默认行为预先声明；
- 策略版本、审批对象、理由、替代方案、可逆性和有效期都进入 Decision；
- 敏感派生物默认继承上游最严格标签，降级需要明确批准。

#### P9 运行与验证

每次正式运行保存：

- 代码 commit 和 dirty diff；
- 数据、模型、Prompt、配置和筛选规则版本；
- 依赖锁、容器/环境、驱动、硬件；
- 参数、随机 seed、输入、输出和日志；
- 执行者、审批者、起止时间、资源和成本；
- 验收规则、容差、统计方案和排除理由。

#### P10 时空与物理对象

- `observed_at`、`recorded_at`、`ingested_at`、`synced_at` 分开；
- 位置记录坐标系、精度、高程基准、GNSS fix 和敏感位置策略；
- 物理对象具有唯一 ID、父子分装、批次、单位、位置、状态、保管人和稳定性时钟；
- 设备状态来自设备/传感器回执，不由 GUI 截图单独推断；
- 插值、补录和时钟对齐必须标明方法及不确定性。

## 6. 推荐跑通的五个端到端闭环

### 闭环 A：实验数据清洗多人会审（首个 P0）

**为什么先做：** 不依赖真实仪器，却能一次验证证据、协作、审批、隔离执行和多客户端。

```text
桌面只读导入原始数据
→ 异常/单位/重复/身份检查
→ 网页上领域研究者与数据管理员并行审阅
→ 冲突仲裁
→ 批准“输入版本 + 规则 + 样例 diff”
→ 独立 session 对副本执行
→ staging 抽样复核
→ 发布清洗文件、异常清单、质检报告和 lineage
```

**人类闸门：**

- 异常值删除/保留；
- 缺失值策略；
- 单位、字段、样本身份和排除标准；
- 最终发布。

**硬验收：**

- 原始文件 hash 100% 不变；
- 人工注入的单位错误、错连、测试集泄漏、时间错位全部检出；
- 关键结构冲突不做 last-write-wins；
- 输入或规则改变后旧批准自动失效；
- 增量重算与全量重算一致；
- 手机只做通知/ack，信息不足时不能批准高风险规则。

### 闭环 B：无源码论文 Baseline + HPC 托管 + 独立复现（P0/P1）

```text
论文 claim/公式/伪代码
→ 实现假设与缺口表
→ 数据/指标审批
→ 环境漂移检查
→ 远程作业提交与长期监控
→ 失败归因/checkpoint 恢复
→ 图表逐元素证据
→ 清洁环境独立复跑
→ 差异说明和复现结论
```

**完成可以是“可解释地复现失败”**，不要求强行达到论文指标。

**硬验收：**

- 连续托管 ≥72 小时，客户端重启/断网不丢状态；
- 同一作业不重复提交，成本不越过批准预算；
- 代码、数据、seed、环境、日志、输出和论文数字全链路；
- 独立复现环境看不到作者隐式缓存和个人凭据；
- 两个独立复现线程在揭盲前互不可见。

### 闭环 C：Idea/科学结论的独立证据审查（K2 → K1）

```text
定义 claim 与检索协议
→ 两名/两组审查者在 sealed workspace 独立检索和评分
→ 提交后揭盲
→ 自动对齐遗漏、支持、反驳和限定
→ 第三人仲裁
→ 共同收敛成研究决策
→ 持续监测新论文、更正和撤稿
```

**硬验收：**

- 揭盲前搜索、通知、缓存、文件名和模型上下文零泄漏；
- “未发现先例”带完整检索覆盖边界；
- 原始独立意见不被仲裁结果覆盖；
- 新来源状态变化后自动标记受影响结论。

### 闭环 D：仪器异常跨班次处置（第二阶段）

```text
仪器电脑只读监控
→ 异常、截图、日志和样本队列形成证据包
→ 手机告警并 ack
→ 网页上值班人、设备管理员、PI 讨论
→ 高风险动作双人批准
→ Computer Use 取得仪器独占 lease
→ 执行暂停/导出/恢复并取设备回执
→ 结构化交班 offer/accept
→ 完成或升级现场接管
```

**硬验收：**

- 4 个线程并发时 GUI、凭据、目录和截图零串扰；
- 同一仪器只有一个 controller；
- 弹窗/重连后重新识别目标；
- 高风险动作没有 quorum 时 100% 拒绝；
- 崩溃重试不重复进样、停机或提交；
- PLC、急停和硬件联锁永远不被绕过。

### 闭环 E：相机陷阱布设—回收或 CTD—采水—化验（P1/P2）

**相机陷阱版本：**

- 手机扫码、BLE、照片、GNSS；
- 连续数天离线；
- 两人离线冲突不能自动覆盖；
- 回收媒体自动匹配设备和部署周期；
- 敏感物种位置按角色模糊化。

**CTD 版本：**

- 船钟、CTD 钟、手机钟分别记录；
- 采水触发、瓶号、压力、坐标、扫码分装和化验结果一一对应；
- 卫星断网后按稳定 event ID 合并，不重复采水事件；
- 绞车、舱门和航行安全由人及设备系统负责。

## 7. 工程优先级与实施顺序

### 7.1 P0 不可绕过的不变量

无论做哪个场景，先满足：

1. 原始输入不可覆盖。
2. 正式 claim 可追溯；无证据时明确未知。
3. R3/R4 有结构化人类批准。
4. 外部写入唯一、幂等、有回执。
5. 并发 session 和共享资源均有隔离/租约。
6. 敏感数据遵守驻留、出站、缓存和导出策略。
7. 失败、负结果、停止和不确定状态可作为正式输出。

### 7.2 建议分期

| 阶段 | 工程范围 | 推荐闭环 | 出口条件 |
| --- | --- | --- | --- |
| P0 | F1 + F3 + F4 + F6-min | 数据清洗多人会审；Benchmark 适配 | 不可变原件、证据、审批失效、持久任务和唯一外部写入路径通过 |
| P1 | F2 四会话隔离 + F5 + F3-HPC | Baseline/HPC；独立证据审查；相机陷阱 | 虚拟键鼠/显示零串扰、跨端同步、长任务恢复和离线冲突通过 |
| P2 | F6 仪器连接 + 领域对象 package | 仪器异常跨班次；CTD/冷链 | 有真实设备方、安全负责人和回放/仿真故障集 |
| P3 | K4 联邦、临床策略、受控物理闭环 | 多中心队列、同意撤回、自驱实验 | 至少两个真实站点及合规负责人；不能用两个文件夹冒充联邦 |

### 7.3 候选优先级评分

`优先分 = 0.20 真实频率 + 0.20 科研后果/价值 + 0.20 跨需求复用 + 0.15 当前缺口 + 0.15 可量化验收 + 0.10 试点就绪度 - 0.10 集成/合规不确定性`

“演示漂亮度”不计分。优先选择能覆盖至少三类需求、消除一个高风险人工断点、且有真实用户和失败样例的能力。

## 8. 针对 Macaron-V1-Tall 与 35B 模型边界的处理

模板中的“是否部署 Macaron-V1-Tall”和“35B 模型能力边界”不应被写成领域需求、Host 特例或第七个工程模块，应作为 F1–F6 各模块的运行注册与验收维度。

正确问题不是“35B 能不能做科研”，而是：

- 在哪一种任务切片上；
- 对哪一类数据敏感度和风险；
- 在何种工具、上下文和硬件条件下；
- 通过率、置信区间、成本、延迟和失败类型是什么；
- 失败时升级到什么模型、专用工具或人工角色。

建议评测切片：

| 切片 | 核心指标 |
| --- | --- |
| 长文精确引用 | claim→正确版本/页/段/图表准确率，虚假锚点率 |
| 公式与方法复现 | 实现偏差、可运行率、指标差、假设标注完整性 |
| Schema/Benchmark | 字段映射、标签泄漏、选项错位、解析正确率 |
| 数据语义质检 | 单位、身份、时间、范围和泄漏错误检出率 |
| Computer Use | 任务成功率、错误 target 率、恢复率、每步成本 |
| 科学审查 | 支持/反驳/限定召回，因果误标率，校准 |
| 长任务 | checkpoint 恢复、重复提交、状态丢失、成本超限 |

模型评测不能替代系统隔离。盲态信息屏障、外发策略、资源租约和审批必须由平台强制，即使模型在测试集上从不犯错。

## 9. 对原需求采集模板的改进

原模板应在“输入/输出/验收”之外增加以下字段：

### 9.1 角色与协作

- 涉及哪些人、Agent、设备、机构？
- 谁可看、评论、修改、运行、批准、签名、外发？
- 协作拓扑是 K1 共编、K2 盲态、K3 交班还是 K4 联邦？
- 是否要求职责分离或多人 quorum？

### 9.2 状态与写回

- 任务当前状态和终态是什么？
- 结果要写回 ELN、LIMS、EDC、代码仓库、论文、日历还是设备？
- 谁是当前 owner，完成后由谁接手？
- 事实何时失效，谁负责复核？

### 9.3 证据与版本

- 事实需要定位到 URL、页、图、表、数据行、代码还是仪器 run？
- 输入、规则、模型、环境和输出如何版本化？
- 来源更正、数据变化或规则修改后，哪些下游必须失效？
- “未发现”“阴性结果”“停止”怎样保存和复核？

### 9.4 风险与人类参与

不要默认“Agent 自动完成，仅以下环节需要人”，而应分别填写：

- Agent 可以自主执行什么；
- Agent 只能建议什么；
- 人必须亲自执行什么；
- 哪个角色必须批准什么；
- 无人响应、超时或意见冲突时怎么办。

### 9.5 并发、隔离和恢复

- 共享哪些账号、窗口、文件、GPU、仪器或样本？
- 是否允许并发读/写，资源锁粒度是什么？
- 重试会不会重复预约、收费、发送、删除、进样或停机？
- 部分成功、崩溃、断网和接管如何恢复？

### 9.6 多客户端与离线

- 哪些动作发生在手机、桌面和网页？
- 是否需要扫码、照片、语音、GNSS、BLE 或传感器？
- 弱网可持续多久？
- 离线冲突、设备丢失和撤权后写入如何处理？

### 9.7 可量化验收

- 正常、歧义、断网/崩溃、权限不足、来源变化、恶意/污染输入六类路径均需样例。
- 分开记录完整性、忠实性、可追溯性、成功率、时延、成本和人工节省。
- 统计隐藏人工劳动；后台人工补数据、修失败不能算 Agent 自动完成。

## 10. 反“伪闭环”检查表

以下情况不能算通用能力已完成：

- 用三篇结构良好的公开论文或干净 CSV，只测 happy path。
- claim 只链到论文首页或 URL，不能定位支持句、图、表和版本。
- 给出“可信度 0.87”，却没有 rubric、偏倚、反证和校准。
- 把搜索不到写成“没有先例”，未保存 query、数据库和日期。
- 多窗口共用浏览器 profile、剪贴板、焦点或下载目录，却称为多线程隔离。
- 两个 Agent 在同一上下文先后回答，却称为独立盲审。
- UI 隐藏盲审结果，但通知、缓存、搜索或模型上下文已经泄漏。
- 交班只是发送总结，没有唯一 owner lease 和 receiver accept。
- 把原始数据复制到中心，再声称完成联邦计算。
- 多人协作只是发链接，没有权限、评论、提案、批准、冲突和作者归属。
- 多客户端只是响应式网页，没有离线、通知、接力和 exactly-once。
- Agent 生成脚本但未真实运行，或修改数据/Prompt/指标后仍称复现。
- 只测任务成功率，不测错引、标签泄漏、原件覆盖、错误发布和撤稿传播。
- 为每个 demo 新建一套 IPC、MCP、registry、证据或写入路径。

## 11. 工程完成定义

一个通用能力或真实闭环只有同时满足以下条件才算完成：

1. 使用生产公共合同和标准 manifest 组合，不依赖领域 ID、展示样例或 Host 特例。
2. 正常路径和六类失败路径均有自动化或可重复验收。
3. 关键 claim、数据变化、运行和审批进入同一 provenance/event 体系。
4. 多线程、多人、跨端状态没有第二套旁路。
5. 原始对象、历史版本、失败和异议没有被最终结果覆盖。
6. 外部写入有唯一请求、幂等键、审批、资源版本、执行回执和完成验证。
7. 对当前做不到的部分明确返回 `unknown / needs human / blocked by policy / external state uncertain`，不伪造完成。
8. 至少有一组真实规模、真实权限、真实失败样例和真实下游决策的用户试点。

最终衡量标准不是“Agent 是否给出了一个好答案”，而是：

> **当输入脏、来源变、网络断、线程并发、人员交班、权限撤回、设备异常或结论被质疑时，系统仍能保持证据完整、状态一致、资源不串扰、人类责任清楚，并且可以安全恢复或明确停下。**
