# Agent Host Verification Chain Design

## Context

SciForge currently intends Agent Host to own user-level completion truth, while Browser Host, Computer Use, artifact generators, and UI surfaces provide bounded operations and evidence. Recent browser-search runs exposed a gap: a run can show `Check: verified` even when the answer only summarizes low-information pages such as an arXiv homepage or login page. The UI-visible status is therefore not reliably grounded in a task-level verifier decision.

This design unifies the completion chain around Agent Host while keeping verification adaptive to the request type. The goal is not to run one heavyweight semantic verifier for every answer. The goal is to make every user-visible completion status flow through Agent Host-owned acceptance semantics.

## Principles

Agent Host owns the intelligent parts of task understanding, acceptance criteria, repair decisions, and final completion truth.

UI must not infer whether a user task is verified. UI may render statuses and apply defensive fallbacks, but the source of truth is Agent Host.

Verifier execution is scenario-dependent. Some requests require no external verifier, some require deterministic evidence or state checks, and some require semantic evidence checks.

Verifier output is an input to Agent Host decision-making, not just a display artifact.

Failures should prefer bounded automatic repair before being exposed to the user. Repair loops must have explicit budgets.

## Unified Flow

```text
UserRequest
-> Agent Host intent understanding
-> AcceptanceSpec
-> VerificationPlan
-> tool/browser/desktop/file operations
-> EvidenceBundle
-> AnswerCandidate
-> VerifierResult
-> Agent Host decision
   -> continue repair
   -> answer verified
   -> answer completed without verification
   -> answer partial
   -> blocked
-> CompletionTruth
-> UI render
```

## Core Objects

### AcceptanceSpec

`AcceptanceSpec` describes what would satisfy the user request. It is generated by Agent Host and differs by scenario.

Examples:

- Browser research: source constraints, topic, time window, required item fields, report language, evidence requirements.
- Desktop operation: target app state, required visual/state evidence, allowed operation scope.
- File analysis: required input files, analysis scope, output shape, citation requirements.
- Ordinary chat or code explanation: may mark external verification as not required.

### VerificationPlan

`VerificationPlan` describes how to verify an answer candidate for this request.

It should select from stable verifier capabilities rather than inventing arbitrary one-off verifier code. Agent Host provides the plan; reusable verifier modules execute it.

Suggested verifier capability types:

- `refs`: required evidence refs exist and belong to the current run.
- `source_relevance`: source pages are task-relevant and not only navigation, login, homepage, policy, or other low-information pages.
- `temporal`: time constraints such as today, latest, current, or a relative window are satisfied or explicitly unresolved.
- `field_coverage`: required fields exist for structured results.
- `action_state`: desktop or browser action reached the requested visible/stateful condition.
- `artifact`: generated artifacts exist, are readable, and match requested format constraints.
- `semantic_entailment`: answer claims are supported by evidence when deterministic checks are insufficient.
- `not_required`: Agent Host decided no verifier should run for this request.

### VerifierResult

Verifier results are returned to Agent Host before final answer generation.

```ts
type VerificationStatus =
  | "satisfied"
  | "repairable"
  | "partial"
  | "blocked"
  | "not_required";

interface VerifierResult {
  status: VerificationStatus;
  issues: Array<{
    code: string;
    message: string;
    evidenceRefs?: string[];
  }>;
  repairHints: Array<{
    action: string;
    reason: string;
  }>;
  satisfiedEvidenceRefs: string[];
}
```

`repairable` is internal to Agent Host. It should not be rendered as the final UI state.

### CompletionTruth

`CompletionTruth` is the only user-visible completion status source.

Suggested UI-facing statuses:

- `verified`: evidence or state verification passed.
- `completed`: Agent Host completed the request and determined verifier execution was not required.
- `partial`: relevant evidence exists, but the request is not fully satisfied.
- `blocked`: no task-relevant evidence exists, a required operation failed, or repair budget was exhausted without useful evidence.

`not_required` should not render as `verified`; it should render as `completed`.

## Bounded Repair

When verification fails with `repairable`, Agent Host should try to repair automatically before answering.

Repair budgets:

- Attempt budget: maximum number of repair rounds.
- Operation budget: maximum extra browser, desktop, file, or tool operations per round.
- Repeated-failure budget: stop early when the same failure recurs, such as only reading low-information pages or repeatedly finding no relevant source.

After budget exhaustion:

- If there is relevant but incomplete evidence, final status is `partial`.
- If there is no task-relevant evidence, final status is `blocked`.
- If the evidence supports a real no-result conclusion, Agent Host may return a verified no-result answer when the no-result evidence itself satisfies the acceptance spec.

## Browser Research Example

For a request such as "search arXiv for papers from the last week about virtual cells and write a Chinese report", Agent Host should generate an acceptance spec with:

- source constraint: arXiv or acceptable scholarly sources, depending on user wording.
- topic constraint: virtual cells and semantically equivalent terms.
- time constraint: relative window ending at the current date.
- required result type: paper-like items or a source-supported no-result conclusion.
- output constraint: Chinese systematic report.

If Browser Host only returns arXiv homepage and login pages, verifier should return `repairable` with issues such as:

- low-information sources.
- no paper/search-result evidence.
- topic not established.
- time window not established.

Agent Host should then repair by changing query strategy, opening search-result pages or concrete paper pages, and reading page text. If repair still fails, the final status should be `blocked` rather than `verified`.

## UI Contract

UI must render the status supplied by Agent Host completion truth.

UI may apply defensive fallback behavior:

- Missing completion truth must not render as `verified`.
- Unknown status must render conservatively as `partial` or `blocked`.
- UI may show verifier issues and evidence refs, but it must not decide task satisfaction.

## Non-Goals

This design does not require a heavyweight LLM semantic verifier for every answer.

This design does not move task-intent understanding into Browser Host, Computer Use, or UI.

This design does not require every operation module to know the full user task. Modules may expose structured facts, refs, and bounded-operation results; Agent Host composes them into user-level truth.

## Testing Strategy

Unit tests should cover Agent Host generation of acceptance specs and verification plans for browser research, desktop action, file analysis, and no-verifier chat/code-answer scenarios.

Verifier tests should cover low-information pages, missing current-run refs, temporal mismatch, field coverage mismatch, artifact existence, desktop state mismatch, semantic support failure, and no-result evidence.

Integration tests should assert that UI `verified` only appears when Agent Host completion truth is `verified`, and that homepage/login-only browser evidence cannot produce a verified research answer.

Repair tests should assert that repairable verifier failures trigger bounded retries and that budget exhaustion produces `partial` or `blocked` according to available evidence.
