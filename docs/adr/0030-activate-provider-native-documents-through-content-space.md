# Activate provider-native documents through Content Space

Provider-native document operations, including the current MDoc capability, belong to Content Space. A trusted installed `ContentSpaceProvider` contributes its exact operation family through standard composition, but composition only registers candidates. Shared Documents and `DocumentProvider` do not participate in this delivery; OpenContent is the only current Provider, but it does not enter the provider-neutral contract or Host routing.

Provider-declared readiness and current invocation admission are separate. Readiness remains exactly `poc_only`, `blocked_by_contract`, or `production_ready`; admission separately evaluates the exact caller, current Principal, Broker authority, resource capability, trusted audience, platform Gate, transfer limits, and current Provider binding. An admitted PoC invocation remains `poc_only`, and `blocked_by_contract` is never admitted.

As amended by ADR-0037, Content Space has no static verification-profile contract or package contribution. Every `poc_only` invocation requires a v2 Provider Binding Attestation for the exact Provider Instance, full current Principal, opaque external subject, and opaque binding revision. Content Space obtains it only through the pinned Provider and carries the exact expectation in-process; immediately before each remote business call or Connector-owned supplier subprocess, the Provider passes it to the Connector, which reauthenticates the actual current session and requires an exact recomputed match. Unbind, rebind, credential replacement, stable external-subject identity change, or binding-revision drift therefore fails before business dispatch rather than reusing stale authorization; mutable account and display labels are not identity keys. Host assurance is not an external account class, and raw external account identifiers never become caller input or portable authority.

The OpenContent adapter makes no production claim. Packaged acceptance attaches evidence only to the exact operation and scope exercised, never changes `poc_only` readiness, and never widens a sibling operation. The [OpenContent capability matrix](../opencontent-skill-capability-matrix.md) is the sole public ledger for current exact outcomes; it records no native-document live success and zero `production_ready` operations. The six ordinary personal/Team-library file operations, all ten Team Administration operations, and safely contract-shaped native/extended operations are `poc_only` with reason `runtime_authorization_required`. Provider discovery can enumerate an installed Provider Instance, while an invocation additionally requires the current user's binding and real Provider authorization. Team deletion is absent from the contract and runtime.

The private supplier overlay is optional runtime data, not the OpenContent integration itself. Without it, SciForge and public Content Space/Connector behavior continue normally, the native-document feature is absent, session-backed `getCurrentPrincipal` remains the only extended PoC candidate, and the other 49 extended operations fail closed before supplier dispatch. With a statically verified overlay, the same canonical Provider → Connector path exposes the full 20-operation native-document and 50-operation extended inventories; attachment presence changes neither readiness nor runtime authorization. The separately distributed `opencontent-base` Agent skill is also optional and is not this overlay: Provider selection and ordinary/Team operations do not require it. The Connector-owned snapshot separately freezes 86 supplier inventory commands and the exact 50-command admitted adapter union. The supplier `download`, `file-list`, `kbox-list`, `file-internal-link`, `meta-modeldata`, and `collab-link` commands remain inventory-only; ordinary `listEntries` and download use the typed Connector path, and native PDF export remains `native-document:export`. Inventory is not packaged callability evidence.

Nine safely shaped native-document operations and 40 extended operations remain PoC-only. Eleven native-document operations are `blocked_by_contract`: ten hash-bound mutations—`update`, `insert`, `edit`, `undo`, `redo`, `comment-create`, `comment-reply`, `comment-solve`, `comment-reopen`, and `comment-delete`—because the Provider does not atomically compare their `baseHash` as part of the mutation, plus `import` because pinned attachment `1.0.1` exposes no source-identity or content postcondition. A local probe, plan receipt, pre-read, write-time re-read, or post-write digest cannot close the mutation race; inventory presence cannot make import executable. Ten extended operations are `blocked_by_contract`, in catalog order: `resolveInternalLink`, `listMetadataChoices`, `updateFileVersion`, `searchUsers`, `searchDepartments`, `searchPositions`, `searchGroups`, `resolveCollaborationInvitation`, `listKnowledgeCollections`, and `searchKnowledgeCollections`. PDF export remains a format of `native-document:export`, and directory enumeration remains ordinary `listEntries`.

`updateFileVersion` remains blocked before Provider invocation. The supplier materials neither freeze an exact expected version identity nor prove one atomic compare-and-update operation, and they use inconsistent `UPDATE` and `UPGRADE` names for same-file upload semantics. A read followed by upload is not CAS. `observeImmutableVersion` also remains blocked: a mutable file identity, version-like value, or digest does not prove immutable retention and version-specific retrieval, so OpenContent cannot issue an `ArtifactReference`.

Cloud Collaboration remains the owner of any future Project shared-root intent. The current Content Space and OpenContent Provider contracts contain no Project provisioning capability, operation, intent/report schema, or Provider port. A future Project-owning integration must introduce an authoritative binding and identity contract through a separately reviewed change; it cannot reuse ordinary Team administration as Project authority. Project archival or deletion never cascades to the Provider Content Container or its content.

The separate Agent administration operation that creates a shared Content Container does not accept an owner in Agent input. The Broker's current Principal supplies the owner, and the Provider verifies that it maps to the authenticated current external session; an Agent cannot nominate itself, another user, a Coordinator, or an arbitrary Provider account as owner. This is not Project provisioning or Cloud Task handoff.

Administration v3 membership page items are exactly `{ member }`, and mutation receipts reuse that typed reference alongside exact root/result fields; no public member-role mutation or ownership-transfer operation remains. `updateSpace`, `pinSpace`, `unpinSpace`, `addMember`, and `removeMember` accept no `expectedRevision`, return no Administration revision, and declare `concurrency.revision: "none"`, because the OpenContent Team supplier surface exposes no atomic expected-state field. Observation and post-write reconciliation prove bounded receipts, not CAS. Content Space binds all ten Administration outputs to the exact request and Broker authority; a mismatch on a read is `provider_unavailable`, while a mismatch on a write/destructive operation is `outcome_unknown`, and neither is retried automatically.

Production promotion is a separate code-and-documentation decision for one exact operation. Evidence must come from a current packaged application through Broker → Content Space → pinned Provider → Connector, identify the exact build, Provider Instance, complete Principal/assurance, opaque binding attestation, authority/root, audience, operation, enforced limits, and outcome, and cover relevant authorization and failure cases. A source run, direct API/CLI probe, mock, skill installation, successful PoC invocation, or sibling success cannot promote readiness.

Once the exact invocation is admitted against an exact Broker resource, the Agent needs no separate Human confirmation for a non-destructive ordinary content write. That delegation is neither standing root-administration authority nor destructive-operation approval: `updateSpace`, `pinSpace`, `unpinSpace`, `addMember`, `removeMember`, and every native-document or extended destructive operation each require fresh per-invocation confirmation, and the Broker rejects a missing confirmation before Provider binding or dispatch. An ordinary child, feature-selection, or Provider-administration resource cannot substitute for that confirmation. Exact-target and collision safeguards still apply after approval. A contracted multi-resource operation first receives a short-lived Broker selection bound to its canonical request and every already delegated constituent; direct handles never acquire ambient sibling authority. Library roots remain administration targets only, although they may serve as destinations for ordinary child operations.

Agent transfer requests name only a validated Workspace-relative path. Host transfer handles stay inside Content Space, Providers receive only bounded byte ports, and Host byte maxima are enforced for the actual transfer. The same invocation carries a non-serializable Host Principal guard and the exact expected Provider Binding Attestation through the unique Provider/Connector path. Identity and binding revalidation limit authority drift but do not substitute for an atomic Provider concurrency contract.

This decision supersedes ADR-0005's universal prepare-confirm-apply rule and ADR-0029's separate confirmation for every Agent write only for non-destructive writes against delegated Content Space resources; fresh confirmation for destructive effects, root selection, target bounding, explicit effect classification, and exact-target safeguards remain. It supersedes ADR-0010's exclusive assignment of all provider-native document semantics to Shared Documents and ADR-0025's deferral of every OpenContent MDoc/document port only for this ContentSpaceProvider capability; the separate provider-neutral Shared Documents and DocumentProvider target remains deferred.

The OpenContent Connector, Provider integration, and SDK documentation are public source. Supplier wire/transport/process isolation belong to the Connector domain package; receipt-to-Content-Space semantics belong to the Provider domain package. They are not a separately versioned runtime feature package. The Connector's package manifest separately declares one public package-owned deployment configuration that binds the fixed Provider Instance to an absolute HTTPS origin. Source and packaged builds use one exact path each with no fallback; missing or invalid configuration preserves discovery but gates all Provider-backed calls before settings, credentials, network, or supplier execution. Node-local unbind remains available without the configuration, deletes the fixed-slot local credential, and performs no Provider business call. Generic packaging captures one immutable declaration/receipt composition and passes it unchanged to after-pack verification: active targets must match their exact size and digest, while inactive declared targets must be absent. The packaged copy lives under `resources/domain-deployments/**`; supplier assets remain a distinct optional receipt-backed overlay under `internal/opencontent/**` in source and `resources/opencontent/**` when packaged. The public Provider configuration is included in npm tarballs and is independent of user credentials and the optional private Agent skill ZIP.

The complete current call chain is recorded in the [Content Space architecture guide](../content-space-architecture.md), detailed operation evidence in the [OpenContent capability matrix](../opencontent-skill-capability-matrix.md), and the public/private boundary in the [attachment distribution guide](../opencontent-attachment-distribution.md).
