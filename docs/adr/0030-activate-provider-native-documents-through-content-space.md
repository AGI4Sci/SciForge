# Activate provider-native documents through Content Space

Provider-native document operations, including the current MDoc capability, belong to Content Space. A trusted installed `ContentSpaceProvider` contributes its exact operation family through standard composition, but composition only registers candidates. Shared Documents and `DocumentProvider` do not participate in this delivery; OpenContent is the only current Provider, but it does not enter the provider-neutral contract or Host routing.

Readiness is exact and per operation. Ordinary product dispatch admits `production_ready` / `available`; a `poc_only` operation remains unavailable unless a separately reviewed package-owned Content Space profile matches the exact Provider Instance, complete Host Principal snapshot and assurance, authority, operation, audience, zero upload/download limits, and validity window of at most 24 hours. Host assurance is not an external Provider account class. The Connector currently supplies no attested external account subject or opaque binding revision, so provider-instance authority can admit only the read-only `list-containers` bootstrap and exact Broker-bound content-root authority can admit only reads; mutation and administration profiles fail composition until such attestation exists. Manifest and runtime profile values must match exactly, invalid/drifting/duplicate profiles fail composition, and default product composition installs no active profile. The policy narrows only that invocation, does not rewrite Provider readiness, and cannot admit `blocked_by_contract`. Caller input, renderer state, an Agent request, prompt text, a Task, an environment variable, ordinary configuration, package presence, or success of a sibling operation cannot install, select, widen, or promote it.

The OpenContent adapter has zero `live_verified` operations and makes no production claim. The six ordinary personal/Team-library file operations, all ten Team Administration operations, and safely contract-shaped native/extended operations are `poc_only` with reason `verification_profile_required`. Provider discovery can enumerate an installed Provider Instance, but discovery is not live evidence and admits no Provider business operation. Team deletion is absent from the contract and runtime.

The private supplier attachment is optional runtime data, not the OpenContent integration itself. Without it, Content Space does not register the native-document feature; the two public Team-governance extended operations remain PoC candidates and the other 52 extended operations are blocked before supplier dispatch. With a statically verified overlay, the Provider contributes exactly 20 native-document and 54 extended-operation candidates. Ten safely shaped native-document operations and 53 extended operations remain PoC-only. Ten hash-bound native-document mutations—`update`, `insert`, `edit`, `undo`, `redo`, `comment-create`, `comment-reply`, `comment-solve`, `comment-reopen`, and `comment-delete`—remain `blocked_by_contract` because the Provider does not atomically compare their `baseHash` as part of the mutation. A local probe, plan receipt, pre-read, write-time re-read, or post-write digest cannot close that race.

`updateFileVersion` remains blocked before Provider invocation. The supplier materials neither freeze an exact expected version identity nor prove one atomic compare-and-update operation, and they use inconsistent `UPDATE` and `UPGRADE` names for same-file upload semantics. A read followed by upload is not CAS. `observeImmutableVersion` also remains blocked: a mutable file identity, version-like value, or digest does not prove immutable retention and version-specific retrieval, so OpenContent cannot issue an `ArtifactReference`.

Cloud Collaboration is the sole source of Project shared-library provisioning intent. Content Space publishes no generic `content-space.agent-provision-project` capability, and the Provider operation `provision-project` remains `blocked_by_contract`. A provider-neutral `ProjectContentSpaceProvisioningPort` may remain composed but dormant until a Project-owning consumer supplies an authoritative Project Content Space Binding, desired owner and member set, and verified identity mappings. Project archival or deletion never cascades to the Provider library or its content. Project provisioning does not create Cloud Task handoff; no Task-specific Content Space port exists, and Cloud Collaboration must first own typed Task file intents and exact Task-turn resource injection and retirement.

Production promotion is a separate code-and-documentation decision for one exact operation. Its evidence must come from a current packaged application through Broker → Content Space → Provider → Connector, identify the exact build, Provider Instance and observed external tenant/account, complete Host Principal snapshot and assurance, root/scope, audience, operation, limits, and outcome, and cover relevant authorization and failure cases. The record must distinguish observed external account evidence from a Connector-attested opaque binding revision; the latter does not exist today. A source run, direct API/CLI probe, mock, attachment install, or successful sibling operation cannot promote readiness. Same-file mutation additionally requires a Provider-atomic expected-version/hash precondition with a deterministic stale conflict and proof of zero mutation. Artifact issuance additionally requires retained immutable versions and exact version-specific retrieval after newer writes. The detailed evidence checklist lives in the [OpenContent capability matrix](../opencontent-skill-capability-matrix.md).

Once both exact operation readiness and an exact Broker resource admit a write, the Agent needs no separate Human confirmation for that invocation. Destructive operations remain separately classified and must name that exact authorized target; the resource cannot widen scope, and collisions or stale state fail closed instead of implicitly overwriting content. A contracted multi-resource operation first receives a short-lived Broker selection bound to its canonical request and every already delegated constituent; direct handles never acquire ambient sibling authority. Library roots remain administration targets only, although they may serve as destinations for ordinary child operations.

Agent transfer requests name only a validated Workspace-relative path. Host transfer handles stay inside Content Space, and Providers receive only bounded byte ports. The same invocation also carries a non-serializable Host Principal guard through the unique Provider/Connector path; it is revalidated before every Connector remote request and every private CLI subprocess dispatch. Principal revalidation limits authority drift but does not substitute for an atomic Provider concurrency contract.

This decision supersedes ADR-0005's universal prepare-confirm-apply rule and ADR-0029's separate confirmation for every Agent write only for delegated Content Space resources; their root-selection, target-bounding, explicit effect classification, and exact-target safeguards remain. It supersedes ADR-0010's exclusive assignment of all provider-native document semantics to Shared Documents and ADR-0025's deferral of every OpenContent MDoc/document port only for this ContentSpaceProvider capability; the separate provider-neutral Shared Documents and DocumentProvider target remains deferred.

The OpenContent Connector, Provider adapter, SDK documentation, and SciForge-authored runtime contracts/adapters are public source. The supplier attachment is installed only as a receipt-backed overlay under `internal/opencontent/**`, remains outside the public workspace and lockfile, and resolves from one fixed source location only after the Connector revalidates its exact receipt identity, root, version, complete inventory, and digests through the public generic integrity module. Packaging copies it to one fixed resource location only after the same static SciForge-owned validation. Official public releases reject non-empty internal composition. The complete boundary is recorded in the [attachment distribution guide](../opencontent-attachment-distribution.md).
