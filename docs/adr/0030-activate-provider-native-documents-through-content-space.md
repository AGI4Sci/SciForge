# Activate provider-native documents through Content Space

Provider-native document operations, including the current MDoc capability, belong to Content Space. A trusted installed ContentSpaceProvider contributes its exact operation family through standard composition, but composition only registers candidates: Content Space dispatches an operation only when the Provider declares that operation `production_ready` with reason `available`. An implemented adapter is therefore neither production admission nor live verification. Shared Documents and DocumentProvider do not participate in this delivery; OpenContent is the only current Provider, but it does not enter the provider-neutral contract or Host routing.

The current OpenContent adapter has zero `live_verified` operations and makes no live-acceptance claim. Its public SDK/facade path nevertheless declares Provider discovery, the six ordinary personal/Team-library file operations, all ten Team Administration operations, and Project Content Directory provisioning `production_ready` with reason `available`; those capabilities do not depend on the separately distributed supplier attachment. The two extended Team-governance operations, member-role change and owner transfer, use the same public Team Administration path and are also `production_ready` / `available`. Team deletion is absent from the contract and runtime.

The private supplier attachment is optional runtime data, not the OpenContent integration itself. When it is absent, Content Space does not register the native-document feature, and it blocks the 52 attachment-backed extended operations before any CLI dispatch. When a valid attachment is installed, the Provider contributes exactly 20 native-document operations and 54 extended operations. Eleven native-document operations are `production_ready`, including the canonical `probe` → `plan` → `edit` chain. Nine direct mutations—`update`, `insert`, `undo`, `redo`, `comment-create`, `comment-reply`, `comment-solve`, `comment-reopen`, and `comment-delete`—remain `blocked_by_contract` because the supplier does not atomically compare their `baseHash` as part of mutation; a prior read cannot close that race. The canonical edit chain instead consumes exact probe/plan evidence and passes its own plan precondition gate.

Of the 54 extended operations, 53 are `production_ready` when the valid attachment is installed; the two Team-governance operations remain available without it. `updateFileVersion` is the sole blocked extended operation because the supplier exposes neither an exact expected version identity nor an atomic compare-and-update operation. `observeImmutableVersion` also remains blocked because a mutable file identity, version number, or digest does not prove immutable retention and version-specific retrieval, so OpenContent cannot issue an `ArtifactReference`.

Cloud Collaboration is the sole source of Project shared-library provisioning intent: the Project Owner supplies the desired content owner, explicit Project Members supply the desired member set, and Project archival or deletion never cascades to the Provider library or its content. The Provider resolves every member through the injected verified-identity binding before any Team or membership write; missing bindings return a typed `pending` report to Cloud instead of guessing an account or partially provisioning the Team. Project provisioning does not create Cloud Task handoff. Task handoff remains deferred: no Task-specific Content Space port exists, and Cloud Collaboration must first own the Project Content Space Binding, typed Task file intents, and exact Task-turn resource injection and retirement.

Once both exact operation readiness and an exact Broker resource admit a write, the Agent needs no separate Human confirmation for that invocation. Destructive operations remain separately classified and must name that exact authorized target; the resource cannot widen scope, and collisions or stale state fail closed instead of implicitly overwriting content. A contracted multi-resource operation first receives a short-lived Broker selection bound to its canonical request and every already delegated constituent; direct handles never acquire ambient sibling authority. Library roots remain administration targets only, although they may serve as destinations for ordinary child operations.

Agent transfer requests name only a validated Workspace-relative path. Host transfer handles stay inside Content Space, and Providers receive only bounded byte ports. The same invocation also carries a non-serializable Host Principal guard through the unique Provider/Connector path; it is revalidated before every Connector remote request and every private CLI subprocess dispatch. Principal revalidation limits authority drift but does not substitute for an atomic Provider concurrency contract.

This decision supersedes ADR-0005's universal prepare-confirm-apply rule and ADR-0029's separate confirmation for every Agent write only for delegated Content Space resources; their root-selection, target-bounding, explicit effect classification, and exact-target safeguards remain. It supersedes ADR-0010's exclusive assignment of all provider-native document semantics to Shared Documents and ADR-0025's deferral of every OpenContent MDoc/document port only for this ContentSpaceProvider capability; the separate provider-neutral Shared Documents and DocumentProvider target remains deferred.

The OpenContent Connector, Provider adapter, SDK documentation, and SciForge-authored runtime
contracts/adapters are public source. Only the original supplier attachment, its extracted files,
and the private distribution overlay under `internal/opencontent/**` are excluded from public
distribution, as recorded in the
[attachment distribution boundary](../opencontent-attachment-distribution.md).
